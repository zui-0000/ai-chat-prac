# 構成を決める

記録日: 2026-11-08 / 対象: Void 1.6.2、Vite+ 1.5.0、oRPC 1.16.2、TanStack Router 1.170.46、TanStack Query 5.107.1、React 19.3.1、TypeScript 7.0.2、tsrs 0.22.0-ts7.1.0-beta、Node.js 26.13.0、pnpm 12.18.0

このリポジトリは、design-system-prac の段階 5「卒業して、実践」をやる場所。お題は AI チャットの画面（design-system-prac の docs/01 の「卒業したら、お題に沿って画面を作る」）。この文書は、雛形を作る前に決めた構成と、その理由をまとめたもの。決める前に、Claude の scratchpad で試作して、組めることを確かめた。

## 土台は Void

[Void](https://void.cloud) は、Vite を作っている VoidZero（2026 年に Cloudflare が買った）のツール。1 つの Vite のプロジェクトに FE と BE を入れて、Cloudflare Workers に 1 つの Worker としてデプロイする。

**理由**:

- いずれ Cloudflare を使いたい。Void は `void deploy` の 1 つで、ビルド・D1 などのリソースの用意・マイグレーション・アップロードまでする
- 使うリソース（D1・KV など）を、コードの import から推測して用意する。`wrangler.jsonc` を手で書かなくてよい
- ツールチェーンの既定が Vite+。`void init` で `--toolchain vite-plus` を選べ、design-system-prac と同じ `vp` の流れで使える
- Cloudflare のアカウントがなくても、ローカルで Cloudflare のランタイム（workerd）とローカルの D1 で動く

**手放すもの**: BE を FE と別にデプロイ・スケールできない。design-system-prac の docs/20 では `apps/web`（React）と `apps/api`（Hono を Bun で動かす）に分けたが、Void では 1 つのアプリにまとまる。TS で言えば、Express を別に立てるのをやめて、Next.js の API Routes に寄せるのに近い。

## API は oRPC の約束から作る

Void にも型の付いた API の仕組み（`void/client` の `fetch`）がある。それを使わず、oRPC を載せた。

### Void の型安全は、コード駆動

Void の型は、Drizzle のスキーマ → ハンドラーが返す値 → `.void/` に生成する `RouteMap` → `void/client` の `fetch` の順に流れる（Void の docs の `guide/type-safety.md`）。入力は `withValidator` で実行時にも確かめるが、出力のスキーマを先に書く場所はなく、返した値から推論される。**型の出どころはサーバーの実装**で、スキーマ駆動ではない。

|                            | Void の作法（コード駆動）                   | oRPC の contract-first（スキーマ駆動）               |
| -------------------------- | ------------------------------------------- | ---------------------------------------------------- |
| 型の出どころ               | サーバーの実装と DB のスキーマ              | 先に書いた約束（入力と出力の両方）                   |
| TS で言えば                | Hono RPC・tRPC                              | OpenAPI・TypeSpec を先に書く                         |
| Spring で言えば            | springdoc（Controller から OpenAPI を作る） | openapi-generator（yaml からインターフェースを作る） |
| 実装より先に FE を作れるか | 作りにくい。ルートを書くまで型がない        | 作れる。約束だけあれば FE と偽物の API が作れる      |

### AI チャットで効く差

| 学びたいこと（design-system-prac の docs/01） | Void の作法だけ                                                                                                         | oRPC                                                                                |
| --------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| 返答が少しずつ届く                            | `void/sse/client` は `EventSource` を包んだもので、リクエストの body を送れない。イベントの型はクライアント側で手で書く | `eventIterator` を約束に書けば、POST の body も、届く 1 つ 1 つの型も約束から決まる |
| 偽物の API（MSW）                             | 偽物が満たすべき約束がない                                                                                              | 偽物も `implement(contract)` するので、形がずれると型エラーになる                   |
| TanStack Query                                | `fetch` はただの async 関数。`queryKey` は自分で管理する                                                                | `@orpc/tanstack-query` が `queryOptions` とキーを約束から作る                       |

チャットは「メッセージを送り、その返答をストリーミングで受け取る」ので、1 行目の差が一番大きい。

**手放すもの**: Void の公式の道から少し外れる。`/rpc` の下は、Void の型付き `fetch` や、ルートごとのキャッシュの対象から外れる。

### oRPC を Void に載せる

Void の docs には oRPC の載せ方は書かれていない。Void のルートは Hono の上で動き、`c.req.raw`（素の `Request`）を読めて、`Response` をそのまま返せる。そこで、catch-all のルート 1 つで、`/rpc` の下をすべて oRPC に渡した。

```ts
// apps/web/src/server/routes/rpc/[...path].ts
const handler = new RPCHandler(router);

const handle = defineHandler(async (c) => {
  const { matched, response } = await handler.handle(c.req.raw, { prefix: "/rpc" });
  return matched ? response : c.notFound();
});

export const GET = handle;
export const POST = handle;
```

試作で確かめたこと:

| 確かめたこと                                                                                 | 結果                                                                         |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 作成・一覧（D1 に書いて読む）                                                                | 通った                                                                       |
| 約束にない入力（空の文字列）                                                                 | `Input validation failed`（400）で弾かれた                                   |
| `eventIterator` のストリーミング                                                             | POST の body を送り、`text/event-stream` で 1 文字ずつ届いた                 |
| 約束にない URL（`/rpc/nope`）                                                                | 404                                                                          |
| `void/db` を `routes/` の外（`src/server/rpc/router.ts`）で import したとき、D1 を推測するか | 推測した（本番ビルドの `dist/ssr/wrangler.json` に `d1_databases` が入った） |
| FE のバンドルに、サーバーのコードや zod が入らないか                                         | 入らなかった（FE は約束の型だけを `import type` で読む）                     |

## FE と BE の置き場所

```text
apps/web/
├── index.html                  ./src/client/main.tsx を読む
├── void.config.ts              sourceDir: "src/server"
├── vite.config.ts              TanStack Router の routesDirectory を src/client/routes に
└── src/                        ソース全体
    ├── client/                 FE（ブラウザで動く）
    │   ├── main.tsx
    │   ├── orpc.ts             oRPC のクライアント
    │   ├── routeTree.gen.ts    TanStack Router が作る
    │   ├── routes/             TanStack Router のルート（Route だけを書く）
    │   └── components/         画面の部品（pages/・layouts/）
    └── server/                 BE（Worker で動く）。Void はここだけを読む
        ├── routes/rpc/[...path].ts   oRPC の受け口
        ├── rpc/router.ts             implement(contract)
        └── db/                       Drizzle のスキーマとマイグレーション
```

### `src` は FE 専用にしない

Vite の雛形では `src` が FE で、Void の雛形ではプロジェクトの直下に `routes/`・`db/` を置く。そのまま使うと、`src` が FE だけを指すことになる。`src` はふつう「ソース全体」の意味なので、`src` の下を `client` と `server` に分けた。

| 案                                           | 形               | 評価                                                          |
| -------------------------------------------- | ---------------- | ------------------------------------------------------------- |
| **A. `src/client` + `src/server`（選んだ）** | 上の形           | `src` の意味が保たれ、FE と BE が対称になる                   |
| B. `src` が FE + `server` が BE              | 直下に `server/` | 雛形に一番近く、設定が少ない。`src` の意味がずれる            |
| C. `client` + `server`（`src` なし）         | 直下に 2 つ      | A より 1 段浅いだけ。`src` を置かない形は TS ではあまり見ない |

**手放すもの**: 雛形の既定から外れるので、3 か所に設定が要る。`index.html` の読み込み先、TanStack Router の `routesDirectory` と `generatedRouteTree`、Void の `sourceDir`。

### `sourceDir: "src"` にしてはいけない

Void の `sourceDir` は、Void の決まりのフォルダ（`pages/`・`routes/`・`middleware/`・`db/` など）をまとめて動かす設定。docs の例は `"src"` だが、そうすると Void が `src/routes` を API のルートとして読み、TanStack Router のルートとぶつかる。Void は `src/server` のように深い場所も指定できる（Void のソースの `validateSourceDir` は、`..` を含まない相対パスなら通す）。

### FE から BE を import させない

dependency-cruiser（`apps/web/.dependency-cruiser.jsonc`）で止める。`vp run lint:deps` で動き、`apps/web` の TS をステージしてコミットするときも動く。

- `client-not-to-server`: `src/client` から `src/server` のファイルを import しない。`import type` も止める。型が要るなら約束に書く
- `client-not-to-server-modules`: `src/client` から `@schema`・`void/db`・`@orpc/server` を import しない。`@schema` は Void が tsconfig の `paths` で当てている名前で、dependency-cruiser は中身のファイルまでたどれない。場所のルールだけだと、`import { messages } from "@schema"` が通ってしまったので、名前で止めるルールを足した
- `server-not-to-client`・`no-circular`

わざと違反するファイルを置いて、止まることを確かめた（`vp run lint:deps` と、コミットのときの `vp staged` の両方）。

#### 設定は apps/web に置く

最初はルートに置いたが、`apps/web` に移した。

**理由**: ルールのほとんどが `apps/web` の中の向き（`src/client` と `src/server`）の話で、ルートに置くと、パスが全部 `^apps/web/src/...` になり、tsconfig も `apps/web/tsconfig.json` を指していた。ルートの設定が、`apps/web` の中の作りを知りすぎていた。TS で言えば、モノレポで ESLint の設定をパッケージごとに置くのと同じで、ルールは守るコードのそばに置く。アプリを足したときも、ルールが混ざらない。

ルートの `vp run lint:deps` は、`vp run -r lint:deps` で各パッケージの `lint:deps` を動かす。

**手放すもの**: 最初にあった `packages-not-to-apps`（packages から apps を import しない）を外した。ワークスペース全体のルールなので、`apps/web` の設定には入らない。パッケージの境界は `package.json` の依存で守る。pnpm は依存を厳しく分けるので、`package.json` に書いていないパッケージは import できない（下の「つまずいたこと」の 4）。抜け道は `../../apps/web/...` のように相対パスでフォルダをまたぐ書き方だけで、ふつうは書かず、書けばレビューで分かる。

## pnpm と依存の設定

design-system-prac の docs/18 の設定を持ってきた（`pmOnFail`・`autoDedupe`・`minimumReleaseAge`・`trustPolicy`）。変えたところは 4 つ。

### 公開から 1 日にした

`minimumReleaseAge` を 2880（2 日）から 1440（1 日）にした。

**理由**: 最新版を早く使いたい。この設定は、乗っ取られたパッケージの悪い版を入れないためのもの。悪い版は、見つかって取り下げられるまでの時間が勝負で、最初の数時間〜1 日でつかまることが多い。1 日待つだけでも、効き目の大半は残る。

**手放すもの**: 見つかるのが遅い攻撃には、2 日より守りが薄くなる。

2026-11-08 の時点では、oRPC 1.16.2（公開から 42 時間）は 1 日なら入り、2 日なら 1.16.1 で止まった。hono 4.13.17 と `@tanstack/router-plugin` 1.169.0 は、公開から 1 日たっていないので、1 つ前の版で止まった。

### Vite+ の道具も除外しない

最初は design-system-prac の `pnpm-workspace.yaml` を写し、`minimumReleaseAgeExclude` に Vite+ の道具（`vite-plus`・`oxlint`・`oxfmt` など）を入れていた。このリストは、design-system-prac で `vp migrate` が勝手に足したもので、design-system-prac の docs/18 でも「足されていたら消す」と決めていた。残しておく理由はないので消した。Vite+ の道具も、公開から 1 日たった版だけを入れる。

消したあと、`node_modules` を消して `vp install` し直し、止まらないことを確かめた。`vp migrate` を動かしたあとに、また足されていたら消す。

### 版を catalog にまとめる

Vite+ のモノレポの雛形（`vp create vite:monorepo`）と同じく、`catalogMode: prefer` にした。`vp add` で足すと、版が `pnpm-workspace.yaml` の catalog に入り、各 `package.json` には `catalog:` と書かれる。TypeScript などを、どのパッケージでも同じ版で使える。npm で言えば、ルートで版を決める `overrides` を、依存を足すたびに自動で書くようなもの。

### catalog の版は固定で書く

catalog の版は、範囲（`^19.3.1`）ではなく固定（`19.3.1`）で書く。実際に入る版は、どちらでも lockfile が決める。違いが出るのは、`vp update` や `autoDedupe` で lockfile を書き直すとき。範囲だと、その範囲の中で版が勝手に動く。

**理由**:

- 配るライブラリがない。範囲で書く一番の理由は、npm に公開したライブラリを使う側で版をまとめやすくすること。`apps/web` も `packages/contract` も `private: true`
- 版が動くのを、自分で上げたときだけにする。そのときに `minimumReleaseAge` と `trustPolicy` がかかる
- `trustPolicyExclude` に版まで書いた例外（tsrs）と食い違わない。範囲だと、新しい版に上がった時点で例外から外れて止まる
- peer の範囲との食い違いに気づける（下の「つまずいたこと」の 5）

npm で言えば、`.npmrc` の `save-exact=true` と `package-lock.json` を一緒に使う形。Renovate なら、アプリ向けの `rangeStrategy: "pin"` と同じ考え方。

**手放すもの**: 修正版が出ても、勝手には入らない。ときどき `vp outdated` で確かめて上げる。

いずれ `packages/ui` で peerDependencies を書くときは、範囲で書く。peer は「この範囲なら動く」という約束なので、固定にすると使う側と食い違いやすい。

#### `savePrefix: ""` で、-E を付けなくても固定で入る

最初は「`vp add` に `-E` を付ける」決まりで固定にしていた。`-E` を忘れると `^` 付きで入るので、`savePrefix: ""` を足して、版を指定しない `vp add` でも固定で入るようにした。design-system-prac では「`-E` で足りる」として入れなかったが、決まりを覚えておくより設定で守る方が確か。

コピーしたリポジトリで、catalog にない `ms` を足して確かめた。

| 足し方                             | 設定なし   | `savePrefix: ""` あり |
| ---------------------------------- | ---------- | --------------------- |
| `vp add ms`（`-E` なし）           | `^2.1.3`   | `2.1.3`               |
| `vp add -E ms`                     | `2.1.3`    | `2.1.3`               |
| `vp add "ms@^2.1.0"`（範囲を指定） | （試さず） | `^2.1.3`              |

範囲を自分で指定して足したときは、範囲のまま書かれる。そのときは catalog の版を固定に直す。

### スクリプトを動かすパッケージ

`void init` が `allowBuilds` に `workerd: true` などを足した。workerd は Cloudflare の Workers のランタイムで、ローカルで Worker を動かすのに要る。design-system-prac では `esbuild: false` だったが、`void init` が `true` にしたので、そのままにした。

## ルートに置く設定ファイル

ルートにも `apps/web` にも、`vite.config.ts` と `tsconfig.json` がある。役目が違う。

### vite.config.ts は、ルートにしか書けない設定がある

| 設定          | Vite+ の docs                                                                                                                                                                                                                          |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lint`・`fmt` | `vp check` は、パッケージのフォルダで動かしても、ワークスペースのルートの `lint`・`fmt` を使う。パッケージに書いても置き換わらない。パッケージごとに変えるときは、ルートの `overrides` に書く（`config/lint.md`・`guide/monorepo.md`） |
| `staged`      | コミットのフックはリポジトリのルートで動き、ルートの設定を読む                                                                                                                                                                         |
| `run.cache`   | ルートの `vite.config.ts` にしか書けない。パッケージに書くとエラーになる（`config/run.md`）                                                                                                                                            |

| ファイル                  | 役目                                                     | npm のモノレポで言えば                                           |
| ------------------------- | -------------------------------------------------------- | ---------------------------------------------------------------- |
| ルートの `vite.config.ts` | ワークスペース全体の lint・整形・コミット時の検査        | ルートの `eslint.config.js`・`.prettierrc`・`lint-staged` の設定 |
| `apps/web/vite.config.ts` | アプリのビルド（React・TanStack Router・Void の plugin） | 各アプリの `vite.config.ts`                                      |

### ルートの tsconfig.json は、なくても vp check の結果が変わらなかった

最初は「ルートの設定ファイルを型チェックするため」に置いた。本当に要るのかを、ルートの `vite.config.ts` にわざと問題を入れ、`tsconfig.json` が「ある・ない」で `vp check` を比べて確かめた。

| わざと入れたもの                                | ある     | ない     |
| ----------------------------------------------- | -------- | -------- |
| 型エラー（`number` に文字列）                   | 見つけた | 見つけた |
| `strict` でしか出ないエラー（暗黙の `any`）     | 見つけた | 見つけた |
| Node の API（`process`・`import.meta.dirname`） | 通った   | 通った   |

- TypeScript 6.0 から `strict` の既定が `true` になり、設定がなくても `strict` で型チェックされる
- Node の型は、`vite-plus` の型から読まれる

それでも置いておく。理由は `tsconfig.json` の先頭のコメントに書いた（既定に頼らない、エディタと結果をそろえる、Vite+ の雛形と同じ形）。`include` は `vite.config.ts` だけに絞る。書かないと、TypeScript の既定（`**/*`）で `apps/` と `packages/` のファイルまで拾う。

最初は `include` に `commitlint.config.js` も入れていたが、`allowJs` がないので JS のファイルは型チェックされておらず、何もしていなかった。外した。

## 型チェックは tsrs

`vp run typecheck`（コミットのときも動く）は、`tsc` ではなく [tsrs](https://oxc.rs/docs/guide/usage/typechecker) で動かす。tsrs は、TypeScript 7 のコンパイラ（Go で書かれている）を Rust に移植したもの。Cloudflare・VoidZero などが TypeScript のチームと協力して作っていて、Oxc のプロジェクトの中にある。2026-10-20 に発表された試験版。

**理由**: 型チェックの道具が Rust に移っていく流れに乗りたい。Void と同じ Cloudflare・VoidZero が作っていて、Oxlint の型を使う lint にも組み込む予定がある。

**手放すもの**:

- 試験版なので、本家の `tsc` と違う結果になることがある（Cloudflare は、エラーを出す順番などが違うと書いている）
- tsrs はどの版も TypeScript 7.1 のベータが元（今の版は `Version 7.1.0-beta (tsrs 0.22.0-ts7.1.0-beta, microsoft/TypeScript@3e9236361fa9)`）。エディタやほかの道具が別の版の TypeScript で型を見ていると、まれに結果が違うことがある

`typescript` 7.0.2 は消さずに残す。tsrs で困ったときに、`typecheck` を `tsc --noEmit` に戻せば済む。

### エディタの TypeScript をリポジトリの版にそろえる

TypeScript 7 のパッケージには、VS Code に元から入っている TypeScript の機能が読む `tsserver.js` がない。エディタで TypeScript 7 を使うには、TypeScript Native Preview の拡張機能（`typescriptteam.native-preview`）が要る。`.vscode/extensions.json` のおすすめに入れた。

動いている言語サーバーのプロセスを見ると、最初は拡張機能に入っている TypeScript（`~/.vscode/extensions/typescriptteam.native-preview-…/tsc --lsp`）が動いていた。版は 7.0.2 で、たまたまリポジトリと同じだったが、拡張機能が自動で更新されると、エディタだけ版が変わる。

`.vscode/settings.json` に 2 つ書いた。

| 設定                                           | 中身                                                                  |
| ---------------------------------------------- | --------------------------------------------------------------------- |
| `"js/ts.experimental.useTsgo": true`           | TypeScript の機能を Native Preview の拡張機能に任せる                 |
| `"js/ts.tsdk.path": "node_modules/typescript"` | 使う TypeScript を、リポジトリの `typescript`（catalog で固定）にする |

ワークスペースの設定に書いただけでは使われない。拡張機能のコードを読むと、ワークスペースを信頼していて、しかも開発者がそのワークスペースで一度許可したときだけ、ワークスペースの `js/ts.tsdk.path` を使う。悪いリポジトリが、開くだけで別のバイナリを動かせないようにするため。最初の 1 回だけ、コマンドパレットの「Select TypeScript Version...」で「Use Workspace Version」を選ぶ。

選んだあと、言語サーバーはリポジトリの `node_modules/.pnpm/@typescript+typescript-darwin-arm64@7.0.2/…/tsc --lsp` に替わった。`js/ts.tsdk.path` は相対パスのまま書き換えられなかった（拡張機能は、同じ場所を指していれば書き換えない）。`useTsgo` は、選んだときに拡張機能がワークスペースの設定に足したもの。

### tsc と同じ結果になるか

| 試したこと                                               | `tsc` 7.0.2                       | tsrs 0.22.0    |
| -------------------------------------------------------- | --------------------------------- | -------------- |
| 正しいコード（Void の `paths`・コメント付きの tsconfig） | 通る                              | 通る           |
| 約束の `text` を `number` にして、実装が合わなくなる     | `router.ts` の `TS2322`・`TS2345` | 同じ場所・番号 |
| FE の型エラー（`<button type="nope">`）                  | `TS2322`                          | `TS2322`       |
| 型エラーがあるときの終了コード                           | 1                                 | 2              |
| 1 回あたりの時間（`apps/web`、5 回の平均）               | 307 ms                            | 203 ms         |

終了コードは違うが、どちらも 0 ではないので、`vp run` もコミット時の検査も失敗として止まる。コピーしたリポジトリで、約束だけを変えたコミットが止まることも確かめた。

時間を測るとき、2 回測り間違えた。出力を捨てて時間だけを見ていたため、tsrs が見つからずにすぐ失敗していたのに気づかなかった。速さを比べるときは、毎回の終了コードを確かめる。

### pnpm の trustPolicy が止めた

`vp add tsrs` は、`trustPolicy: no-downgrade` で「High-risk trust downgrade（possible package takeover）」として止まった。0.22.0 だけでなく、0.12.0 から 0.23.0 まで、どの版でも止まった。

| 確かめたこと                | 結果                                                                                                      |
| --------------------------- | --------------------------------------------------------------------------------------------------------- |
| 名前の履歴                  | 2024 年に別の人（`qidanta`）が中身のない 0.0.0 を出していた。2026-10-10 に Oxc の作者（`boshen`）に移った |
| 0.12.0 以降の公開の証明     | すべて GitHub Actions からの trusted publishing と provenance。前の版より弱い版はない                     |
| provenance の中身（0.22.0） | `github.com/oxc-project/tsrs` の `main` の `.github/workflows/release.yml` でビルドされた                 |
| 今の持ち主                  | `boshen` だけ                                                                                             |

pnpm の docs には「High-risk」の条件が書かれておらず、pnpm 12 はバイナリでソースを読めなかった。名前の持ち主が移ったことを乗っ取りの疑いと見たのだと考えている（確かめてはいない）。

provenance で本物の Oxc のリポジトリから公開されたと確かめたので、`trustPolicyExclude` に例外を足した。例外は名前だけでなく版まで書く（`tsrs@0.22.0-ts7.1.0-beta`）。名前だけにすると、今後どの版も検査を素通りする。版まで書けば、上げるたびに止まるので、そのたびに provenance を確かめて、例外の版を書き換える。例外は `tsrs` の 1 つで済み、プラットフォーム用の `@tsrs/darwin-arm64` は止まらなかった。

## 試作と雛形づくりでつまずいたこと

1. **`void init` が作るのは SSR の Pages の雛形**。SPA にするには、`pages/` を消し、`index.html` と `src/client/main.tsx` を足し、プラグインを `voidReact` から `@vitejs/plugin-react` に替える。Void 本体の `playground/spa` と同じ形
2. **`void init` が書く版の範囲が古い**（`react ^19.2.4`、`hono ^4.11.9`、`vite-plus ^1.4.0`）。`package.json` を書き直し、`vp add -E` で入れ直した
3. **`void init` は `pnpm-workspace.yaml` を書き直す**。そのとき、`allowBuilds` の上のコメントが下にずれた。手で戻した
4. **pnpm は依存を厳しく分ける**。`apps/web` で `@orpc/contract` の型を使うには、`apps/web` 自身の依存に足す必要があった。npm の `node_modules` は平らに並ぶので、依存の依存もたまたま import できてしまうが、pnpm はそれを許さない
5. **`@vitejs/plugin-react` 6.2.1 は `oxc-transform-react` を `>=0.152.0 <0.157.0` で求める**。最新の 0.157.0 を入れると peer の警告が出たので、0.156.0 にした。`vp add -E oxc-transform-react@0.156` のように範囲で指定すると、`-E` を付けても `~0.156.0` のまま `package.json` に書かれ、catalog も使われなかった。catalog の版を直し、`package.json` を `catalog:` に戻した
6. **`run.cache: true` を消した**。Vite+ のモノレポの雛形には入っているが、`package.json` のスクリプトまでキャッシュする。TypeScript 7 の `tsc` は、`vp run` のキャッシュが変更に気づかず、型エラーを見逃す（design-system-prac の docs/01「ツールの決まり」）。消すと既定に戻り、スクリプトはキャッシュされない
7. **TanStack Router のルートのファイルに部品を書くと、`react(only-export-components)` の警告が出る**。`Route` と部品を 1 つのファイルから export すると、Fast Refresh が効かない。design-system-prac と同じく、ルートのファイルには `Route` だけを書き、部品は `components/pages/` に置いた
8. **`routeTree.gen.ts` は、ビルドか開発サーバーの起動で作られる**。作られる前は型チェックが通らないので、コミットする（TanStack Router の docs も勧めている）
9. **マイグレーションは `vp dev` の起動時に自動で流れる**（ログに `Applied 1 migration(s)` と出る）
10. `compatibility_date` は `void init` が `2026-02-24` に固定した。Void のコードに書かれた既定値（`plugin-cloudflare-config.ts`）で、理由は docs に書かれていない。この日付は、Workers の実行時の挙動をその時点のものに固定する（上げると、それ以降の挙動の変更が入る）。上げるかは、Cloudflare にデプロイするときに決める
