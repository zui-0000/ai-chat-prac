# デザインシステムを決める

記録日: 2026-11-14 / 状態: 検討中

画面の部品と見た目の作り方を決める。
design-system-prac で作ったものを元にする。実装は、この方針から UI のチケットを切って進める。

## 決めたこと

| 何を               | どうしたか                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 部品の土台         | Base UI                                                                                    |
| 見た目の書き方     | CSS Modules とデザイントークン（CSS 変数）                                                 |
| styles の構成      | design-system-prac を元にする                                                              |
| 置き場所           | `apps/web/src/client` の中。`packages/ui` には分けない                                     |
| Generative UI      | カタログ型。`features/Chat/GenUI/` に置く                                                  |
| Storybook          | 入れる。`components/ui/`・`styles/`・`features/Chat/` のストーリーを書く                   |
| アイコン           | lucide-react。無いものだけ `assets/icons/` に置く                                          |
| 画像などのファイル | 画面で使うものは `assets/`、URL が決まっているものは `public/`                             |
| CSS の検査         | Stylelint を入れる                                                                         |
| トークンを足す     | 実装しながら、要るときに足す                                                               |
| トークンの値       | デジタル庁を参考にしつつ、モダンな見た目に寄せる                                           |
| 実装のガイド       | Modern Web Guidance を入れる。いつも最新を使う。Base UI とぶつかったら Base UI を優先する  |
| 使う機能の範囲     | Baseline の Newly available（主要ブラウザの最新版で全部使えて、試験中でないもの）          |
| 部品のファイル名   | `ui/`・`features/`・`layouts/`・`pages/` のどれも、1 フォルダ 1 部品で、入口は `index.tsx` |
| 部品の export      | パーツが 1 つなら名前で export。複数なら、使う側で `import * as` して名前空間として使う    |

## Base UI と CSS Modules

モダンなチャットの見た目も、素の CSS で作れる。

| 見た目                                  | 使う CSS                                              |
| --------------------------------------- | ----------------------------------------------------- |
| 入力に合わせて伸びる入力欄              | `field-sizing: content`                               |
| 返答が流れても、一番下に張り付く        | `overflow-anchor` か `flex-direction: column-reverse` |
| 出てくる・消えるときのアニメーション    | 下の「アニメーションの書き分け」、View Transitions    |
| 狭い列でも崩れない Generative UI の部品 | コンテナークエリ（`@container`）                      |
| ダークモード                            | `light-dark()`                                        |

**手放すもの**: AI チャット向けの UI ライブラリ（AI Elements・assistant-ui など）は、shadcn と Tailwind が前提なので使えない。
メッセージ・入力欄・会話の一覧は自分で作る。

### 部品の状態とアニメーションは、Base UI の data 属性で書く

Base UI は、部品の状態を data 属性として要素に付ける（`[data-disabled]`・`[data-highlighted]` など）。
状態の見た目は、JS でクラスを切り替えず、CSS Modules の中で data 属性のセレクターで書く。

アニメーションの書き分け:

| 何                                                 | 使うもの                                                        |
| -------------------------------------------------- | --------------------------------------------------------------- |
| Base UI の部品（ダイアログ・メニュー・Toast など） | Base UI が付ける `[data-starting-style]`・`[data-ending-style]` |
| Base UI の外（新しく出てくるメッセージなど）       | CSS の `@starting-style`                                        |

Base UI の部品は、消えるときのアニメーションが終わるまで要素を残してくれる。CSS の `@starting-style` は、出てくるときにしか効かない。

### 入れ子のポップアップは、Portal の描画先を決める

Base UI のポップアップは、Portal で `<body>` の直下に描かれる。
ダイアログの中の Select のように入れ子にすると、外側の外に描かれて、位置の計算が崩れることがある。そのときは、内側の `Portal` に `container` を渡し、外側の中に描く。

### メニューの項目で画面を移るときは、`render` で `Link` を差し込む

`Menu.Item` の `render` に TanStack Router の `Link` を渡す。キーボード操作と ARIA を保ったまま、画面を移れる。

## Generative UI はカタログ型

Generative UI は、AI の返答の中に部品を出す仕組み。作り方は 2 つある。

| 型                   | AI が出すもの        | 決めたか   |
| -------------------- | -------------------- | ---------- |
| **部品のカタログ型** | 部品の名前と props   | これにした |
| マークアップ型       | JSX や HTML そのもの |            |

**理由**:

- AI は決めてある部品を選ぶだけなので、見た目がデザインシステムの外に出ない
- AI が書いたマークアップを描かないので、安全
- 部品の props を zod で `packages/contract` に書けば、BE は AI の出力を確かめられ、FE は型つきで受け取れる

マークアップ型だと、AI にクラスを書かせるため Tailwind が要る。CSS Modules とは合わない。

```ts
// AI の出力は、判別可能な union になる。画面は kind で部品を選ぶ
type GenUI =
  | { kind: "weather"; props: { city: string; temp: number } }
  | { kind: "table"; props: { columns: string[]; rows: string[][] } };
```

カタログに入れる部品（天気・表など）は、API の設計（ZSCM-27）のあとに決める。

## 置き場所

```text
apps/web/src/client/
├── assets/
│   ├── images/              画像
│   └── icons/               lucide-react に無い、自前の SVG アイコン
├── styles/                  全体の CSS とトークン（design-system-prac と同じ構成）
│   ├── main.css
│   ├── reset.css
│   ├── tokens/
│   └── stories/             トークンの見本のページ
└── components/
    ├── ui/                  汎用の部品（Button・Input・Markdown など）
    ├── features/
    │   ├── Chat/
    │   │   ├── ConversationList/   会話の一覧
    │   │   ├── MessageList/        メッセージの並び
    │   │   ├── Message/            1 つのメッセージ。パーツを描き分ける
    │   │   ├── GenUI/              道具のパーツの描き方（catalog.tsx と部品）
    │   │   └── Composer/           入力欄と送信ボタン
    │   └── Auth/            ログイン・新規登録のフォーム
    ├── layouts/
    └── pages/
```

依存の向きは `pages/` → `features/` → `ui/` の一方向。`features/` 同士も import しない（別の機能の中に依存すると、機能ごとに消したり移したりできなくなる）。どちらも dependency-cruiser で止める。

### ファイル名は、どこでも `index.tsx`

```text
ui/Button/                         ui/Dialog/
├── index.tsx                      ├── index.tsx
├── index.module.css               ├── index.module.css
├── index.stories.tsx              ├── index.stories.tsx
└── index.guide.mdx                ├── index.interaction.stories.tsx
                                   └── index.guide.mdx
```

design-system-prac では、`ui/` だけ部品の名前のファイル（`Button/Button.tsx`）だった。このリポジトリでは `ui/` も `index.tsx` にそろえる。

**理由**:

- import のパスを拡張子まで書く決まりなので、`index.tsx` にしても import は短くならない。どちらにしても `.../Button/index.tsx` か `.../Button/Button.tsx` と書く。それなら、決まりを 1 つにそろえる
- ストーリーや文書の名前も、どこでも `index.stories.tsx`・`index.guide.mdx` になる

**手放すもの**: エディタのタブが `index.tsx` だらけになる。VS Code の `workbench.editor.customLabels.patterns` で、タブにフォルダの名前を出す。

### パーツが複数の部品は、名前空間で使う

| 部品                                            | export の形                                   | 使う側                                                             |
| ----------------------------------------------- | --------------------------------------------- | ------------------------------------------------------------------ |
| パーツが 1 つ（Button・Input・Switch・Tooltip） | 名前で export                                 | `import { Button } from ".../Button/index.tsx"`                    |
| パーツが複数（Dialog・Menu・Field・Form）       | パーツを名前で export（`Root`・`Title` など） | `import * as Dialog from ".../Dialog/index.tsx"` → `<Dialog.Root>` |

design-system-prac では、`AlertDialogTitle`・`MenuItem` のように、平らに export していた。

**理由**: Base UI と同じ `<Dialog.Root>`・`<Dialog.Title>` の形になる。Base UI の docs を読んだ形のまま、このリポジトリの部品も使える。

名前空間の作り方は 3 つあった。

| 作り方                                                                               | 決めたか   | 理由                                                                                                                 |
| ------------------------------------------------------------------------------------ | ---------- | -------------------------------------------------------------------------------------------------------------------- |
| オブジェクトにまとめる（`export const Dialog = { Root }`）                           |            | 部品でないもの（オブジェクト）を export すると、React の Fast Refresh が効かず、保存のたびにページ全体を読み込み直す |
| **使う側で `import * as`**                                                           | これにした | ファイルが 1 つで済み、Fast Refresh も効く。Radix の docs と同じ作法                                                 |
| `export * as Dialog from "./parts.tsx"` だけのファイルを足す（Base UI 自身の作り方） |            | 使う側は `import { Dialog }` で済むが、部品ごとにファイルが 1 つ増える                                               |

**手放すもの**: `import { Title }` と書かれても止められない。「パーツが複数の部品は `import * as` で読む」をルールに書く。

### `packages/ui` に分けない

使うのは `apps/web` だけで、公開もしない。
分けると、CSS Modules とトークンの受け渡し、`#/` のエイリアス・型チェック・テスト・Storybook の設定がパッケージごとに要る。
`ui/` → 外への import を dependency-cruiser で止めておけば、あとでフォルダごと移せる。2 つ目の使い手が出たら分ける。

### Generative UI は Chat の中に置く

Generative UI は、独立した機能ではなく、チャットのメッセージを描く仕組みの一部。
AI の返答は、文字のパーツと道具（tool）のパーツの並びで、道具のパーツを部品で描くのが Generative UI。

```text
AI の返答
├── 文字のパーツ   「東京の天気を調べました。」 → Markdown で描く
└── 道具のパーツ   tool: weather                → 天気カードで描く（呼んでいる途中・結果・失敗で描き分ける）
```

`features/GenUI/` に分けると、`features/Chat/` から別の機能を import することになる。
チャットの外でも使うようになったら、外へ切り出す。

### Markdown の表示は `ui/` に置く

AI の返答を描く部品だが、中身は「Markdown を描く」だけの汎用の部品。
変換した HTML にはクラスが付かないので、`:global` で要素のセレクターを書く CSS Module が要る。それをここ 1 か所に閉じ込める。

## Storybook

| 置き場所                    | 見せるもの                                                                                   |
| --------------------------- | -------------------------------------------------------------------------------------------- |
| `components/ui/`            | 汎用の部品                                                                                   |
| `styles/stories/`           | トークンの見本のページ                                                                       |
| `components/features/Chat/` | メッセージ・Generative UI の部品を、状態ごとに（ストリーミング中・道具の呼び出し中・エラー） |

design-system-prac では「ストーリーは `ui/` だけ」だったが、`features/Chat/` にも広げた。
チャットの部品はこのアプリの主役で、本物の AI で全部の状態を出すのは大変なため。

**確かめること**: `vite.config.ts` に Void の plugin が入っている。Storybook の中で邪魔をするなら、`viteFinal` で外す。

### 構成は One UI を参考にする

Sansan の One UI の Storybook を参考にする。道具（Storybook 10・Vite 8・Vitest 5・pnpm）がこのリポジトリとほぼ同じ。

```text
はじめに          index.mdx
DesignTokens/     トークンの見本
UI/               components/ui/ の部品
Chat/             components/features/Chat/ の部品
Guidelines/       部品をまたぐ決まり（キーボード操作など）
Interaction/      触ったときの動きの確認
```

- **文書は小さく始める**: 自動の文書（props の表）と、人が書く「いつ使うか」（`index.guide.mdx`）から始める。仕様や種類の文書は要るときに足す
- **文書は部品の隣に置く**: One UI は文書を 1 か所にまとめているが、関係するファイルを部品のフォルダにまとめる決まりに合わせる
- **触ったときの確認は分ける**: `index.interaction.stories.tsx` に play function で書き、`Interaction/` に並べる。addon-vitest でテストとして回す
- **ポップアップの困りごとをストーリーにする**: z-index、スクロールする箱の中、入れ子（Portal の描画先）
- **addon-a11y** でアクセシビリティを確かめる
- **`@storybook/addon-mcp`** は、実装のハーネス（ZSCM-29）で入れる。エージェントが、このリポジトリの部品とストーリーを Storybook から引けるようにする
- Chromatic（見た目の差分を比べるサービス）は、今は入れない。要るなら、Vitest のブラウザのスクリーンショットで足りるかを先に試す

## 画像とアイコン

| 置き場所             | 使い方                                                     | 置くもの                          |
| -------------------- | ---------------------------------------------------------- | --------------------------------- |
| `src/client/assets/` | コードから import する。ビルドでファイル名にハッシュが付く | 画面の中で使う画像・アイコン      |
| `apps/web/public/`   | そのままの名前・パスで配られる                             | favicon、`robots.txt`、OGP の画像 |

- `assets/` は、ファイルが無ければビルドが失敗し、中身を変えるとファイル名も変わる（古いキャッシュが残らない）
- SVG をそのまま import すると URL になり、`currentColor` で色を変えられない。自前のアイコンが出てきたら、手で React の部品にするか、`vite-plugin-svgr` を入れるかを決める
- フォルダは、最初のファイルを置くときに作る（git は空のフォルダを記録できない）

## Stylelint

CSS Modules では、部品ごとに CSS を書く。トークンを使い忘れたり、名前を打ち間違えたりしても、ブラウザは黙って無視する。
Stylelint で、次のことを止める。design-system-prac と同じ。

- 部品の CSS に、色の値（`#fff` など）や色の材料（`--color-primitive-*`）を書く
- 定義のない CSS 変数を使う（`var(--color-primay)` のような打ち間違い）
- 配色（ライト・ダーク）ごとに書き分ける（意味のトークンを使えば、どちらにも切り替わる）

## トークンは要るときに足す

design-system-prac のトークンから始め、部品を作りながら、足りないものを足す。先に全部を決めない。
使わないトークンが増えると、どれを使えばよいか迷うため。

足しそうなもの:

- 動き（時間・イージング）。返答のストリーミングや、出てくるときのアニメーション
- チャット用の意味のトークン（自分のメッセージ・AI のメッセージなど）
- 字間（letter-spacing）。デジタル庁は、文字の大きさで 3 段階に分けている（45px 以上は 0、36〜28px は 0.01em、26px 以下は 0.02em）

## Modern Web Guidance

Chrome のチームが出している、コーディングエージェント向けのスキル。HTML・CSS・JS の今のやり方を、ガイドとして持つ。
エージェントは、UI を書く前に関係するガイドを検索して読む。

- 伸びる入力欄（`field-sizing`）、`@starting-style`、コンテナークエリ、アクセシビリティなどのガイドがある
- 日本語の変換を確定する Enter で送信しないためのガイド（IME-safe enter-to-submit）がある。チャットの入力欄で要る

入れるのは、実装のハーネス（ZSCM-29）で。Chrome のマーケットプレイス（`googlechrome`）から入れる。`claude-plugins-official` の版は v0.0.194 で止まる（README による）。

### いつも最新を使う（1 日待ちの例外）

スキルは、CLI を `npx -y modern-web-guidance@latest` で呼ぶ。pnpm の 1 日待ち（`minimumReleaseAge`）は効かないが、例外として認める。

**理由**:

- 中身は Web の今のやり方そのもので、古い版を使う意味が薄い
- 公開の証明（provenance）があり、`GoogleChrome/modern-web-guidance-src` の `publish.yml` から公開されている。依存とインストール時のスクリプトは無い

### Base UI とぶつかったら Base UI を優先する

ガイドは、ネイティブの `<dialog>`・popover・アンカー配置などを勧めることがある。
Base UI に部品があるものは Base UI を使い、ガイドは CSS と振る舞いの注意点として使う。

### Baseline の目標は Newly available

使ってよい機能は、主要ブラウザ（Chrome・Edge・Safari・Firefox）の最新版で全部使えて、試験中でないもの。
Baseline の Newly available にあたる。ZSCM-29 で `CLAUDE.md` に書く（何も書かないと Widely available になる）。

| 段階                 | 意味                               | 使うか   |
| -------------------- | ---------------------------------- | -------- |
| Limited availability | 一部のブラウザでしか使えない       | 使わない |
| Newly available      | 全部の主要ブラウザの最新版で使える | 使う     |
| Widely available     | Newly になってから 30 か月たった   | 使う     |

**理由**: 練習のアプリで、古いブラウザの利用者を守る必要がない。今の CSS（`field-sizing`・`@starting-style`・View Transitions など）を使いたい。
試験中の機能（Origin Trial など）は使わない。Modern Web Guidance の設定（`set-allow-volatile-features`・`set-allow-origin-trials`）は入れない。

### テレメトリは止めない

Google は、入れた数・エージェントの名前・読んだガイドの ID・検索の言葉を集める。プロンプトとコードは集めない。
検索の言葉は一般的なもの（`"light dismiss dialog"` など）で、アプリの名前やファイル名は入れない決まりなので、止めない。
止めるときは、`DISABLE_TELEMETRY=1` を設定する。

## 見た目の方向性の作り方（仮置き）

まだ調べている途中。確定したら、決めたことに移す。

望みは 2 つ。「良い感じの見た目を提案してほしい」と「その方針で見た目をそろえてほしい」。
それぞれを、得意なものに任せる。

| 望み                   | 受け持つもの                                                                  | いつ             |
| ---------------------- | ----------------------------------------------------------------------------- | ---------------- |
| 見た目を提案してほしい | `frontend-design`（Anthropic のスキル）の考え方と、Claude Design のキャンバス | 最初に 1 回      |
| 見た目をそろえてほしい | トークン、`DESIGN.md`、実装のハーネス（ZSCM-29）                              | 部品を作るたびに |

`frontend-design` は、頼まれた内容から AI がその場で見た目を考える。決めたものはファイルに残らないので、続けて使うとぶれる。
提案をもらったらトークンと `DESIGN.md` に書き写し、それ以降は使わない。

```text
1. frontend-design の考え方で、「日本語の AI チャット。毎日使う道具」の方向性を 2〜3 案作る
2. Claude Design（Artifact の Design の型）のキャンバスに、案ごとのチャット画面を並べ、コメントで直してから選ぶ
3. 選んだ案を、トークンの値（primitive → 意味のトークン）に書き写す
4. 色・書体・余白の使い分けと原則を、DESIGN.md にトークンの名前で書く
```

- `frontend-design` は LP 向けで、大胆さに寄りやすい。頼むときに「チャットは道具。静かに作り、大胆さは 1 か所だけ」と伝える
- `DESIGN.md` には hex でなくトークンの名前を書く。値はトークンの CSS だけに置き、2 か所でずれないようにする
- `DESIGN.md` の形は、awesome-design-md-jp のテンプレートを元にする。Google Stitch の `DESIGN.md` の 9 つの節に、日本語の文字組み（フォールバック・行間・字間・禁則・`palt`）を足したもの

### 見比べるのは Claude Design のキャンバスで

[Claude Design](https://claude.com/product/design) は、Anthropic Labs の、プロトタイプ・スライド・デザインシステムを作る道具。
画面をキャンバスに並べて見比べ、チャットやコメントで直せる。単体の claude.ai/design は 2026-12-14 までに閉じ、Claude の中（Artifact の Design の型）に移った。

| 道具                       | 受け持つもの                                                          |
| -------------------------- | --------------------------------------------------------------------- |
| `frontend-design`          | 見た目の考え方。ありきたりを避ける、大胆さは 1 か所、文言の書き方     |
| Claude Design のキャンバス | 見た目を実際に描いて並べる。Artifact として残るので、あとで開き直せる |

**理由**: 色の値を並べられても、良いかどうか分からない。実物のチャット画面で見比べたほうが選びやすい。

- キャンバスの見本は HTML のモックで、このリポジトリの React と CSS Modules のコードではない。選んだあと、トークンと `DESIGN.md` に書き写す
- デザインシステムが無いと、ありきたりな見た目になりやすいと言われる。だから `frontend-design` の考え方を指示に入れる
- 有料プランでも、使える量に週ごとの上限がある
- **Design System の型と `/design-sync` は、今は使わない**。Storybook と `DESIGN.md` と役割がかぶる。部品がそろってから、キャンバスで本物の部品を使って画面を試したくなったら考える

### あるべき流れ（Figma は want）

AI にはアイデアを広げる仕事を、人には選んで細部を詰める仕事を任せる。
AI を途中に挟むとアイデア出しは速くなるが、UI の細部の詰めは人の手のほうが優れている。

```text
1. デザインシステムを用意する（Figma は want）
2. Claude Design に読み込み、そのデザインシステムでプロトタイプを作る   ← AI で広げる
3. HTML で書き出し、動きを確かめる
4. 人が細部を詰めて、詳細設計にする                                  ← 人が絞る
5. 詳細設計から、トークン・部品・画面を実装する
```

今回は Figma を使わずに始める。

| 段階                     | Figma を使わない今回                                             | Figma を使うとき（want）         |
| ------------------------ | ---------------------------------------------------------------- | -------------------------------- |
| デザインシステム         | トークンの CSS と `DESIGN.md`                                    | Figma のデザインシステム         |
| 広げる                   | `frontend-design` の考え方と Claude Design のキャンバス          | Figma を読み込んだ Claude Design |
| 細部を詰める（詳細設計） | キャンバスで選んでコメントで直し、Storybook で状態ごとに見て直す | Figma で詳細設計を起こす         |

**Figma を使うときに決めること**: トークンの値を、Figma と CSS のどちらを正にするか。2 か所に手で書くと、片方だけ直してずれる。

### TypeUI は入れない

TypeUI は、見た目の型（Minimal・Modern など）を選んで、`DESIGN.md` や `SKILL.md` としてリポジトリに置く仕組み。

- 型を選ぶ役目は、`frontend-design` の考え方と Claude Design のキャンバスでの見比べで置き換わる。無料の型は、色・書体・余白の数字が中心で浅い
- 原則のスキル（fundamentals）は、design-system-prac の UX のルール（`.claude/rules/ux.md`）と重なる。自分で作ったルールを持ち込む
- 「決めた見た目をファイルにしてリポジトリに残す」という考え方だけ、`DESIGN.md` として借りる

## CLAUDE.md・AGENTS.md・DESIGN.md の違い

| ファイル    | 誰に向けて                                       | 何を書くか               | 自動で読まれるか                             |
| ----------- | ------------------------------------------------ | ------------------------ | -------------------------------------------- |
| `CLAUDE.md` | Claude Code だけ                                 | 作り方・決まり・コマンド | Claude Code が起動時に読む                   |
| `AGENTS.md` | エージェント共通（Codex・Cursor・Copilot など）  | 作り方・決まり・コマンド | 各エージェントが読む。Claude Code は条件つき |
| `DESIGN.md` | 見た目を作るエージェント（Google Stitch が提唱） | 見た目と雰囲気           | どれも自動では読まない                       |

Claude Code の読み方（[Claude Code の docs](https://code.claude.com/docs/en/memory)）:

- `CLAUDE.md`: 作業しているフォルダとその上のものは、起動時に読む。下のフォルダのものは、そのフォルダのファイルを触ったときに読む
- `AGENTS.md`: v2.1.277 から読む。既定では、`CLAUDE.md` が無いときだけ読む（`/config` の Project instructions で変えられる）
- `DESIGN.md`: 特別な扱いはない。ただの Markdown

このリポジトリはルートに `CLAUDE.md` があるので、Void が作った `apps/web/AGENTS.md` は、既定では自動で読まれない。
`CLAUDE.md` が入口として指していて、中身（Void の docs を読む）も `CLAUDE.md` に書いてあるので、困ってはいない。

`DESIGN.md` は、ハーネス（ZSCM-29）で参照させる。`CLAUDE.md` に `@DESIGN.md` と書くと、BE の作業でもいつも読まれる。
FE のファイルを触ったときに読まれるルール（`.claude/rules/` の `paths`）か、部品を作るスキルの手順から参照する。どちらにするかは ZSCM-29 で決める。

## UI のチケット

この方針が決まったら、次のチケットを切る。どれも親はエピック ZSCM-25。

| チケット             | 中身                                                     | 待つもの                       |
| -------------------- | -------------------------------------------------------- | ------------------------------ |
| 見た目の方向性       | 見た目の提案を選び、トークンの値と `DESIGN.md` を決める  | なし（仮置きが確定したら切る） |
| 土台                 | トークン・styles・Storybook・dependency-cruiser のルール | 見た目の方向性                 |
| 汎用の部品           | Button・Input・Markdown など                             | 土台                           |
| チャットの部品       | メッセージ・入力欄・会話の一覧                           | 土台                           |
| Generative UI の部品 | カタログの中身                                           | ZSCM-27                        |

チャットの部品の一覧は、ここでは決めない。機能の方針と見た目の方向性が決まってから、チャットの部品のチケットで決める。

- 機能で、要る部品が変わる（返答を止める → 止めるボタン、会話を消す → 確認ダイアログ、など）
- 見た目で、部品の分け方が変わる（AI の返答を吹き出しにするか、本文のように流すか、など）

置き場所は「置き場所」の決まり（`ui/` と `features/Chat/`）で決まるので、部品が増えても迷わない。

## ほかのチケットへの申し送り

この文書のあちこちに書いた「あとでやること」を、チケットごとにまとめる。

**見た目の方向性**（新しいチケット。仮置きが確定したら切る）

- `frontend-design` の考え方で 2〜3 案を作り、Claude Design のキャンバスにチャット画面を並べて、見比べて選ぶ
- 選んだ案を、トークンの値と `DESIGN.md`（awesome-design-md-jp のテンプレートを元に、トークンの名前で書く）に書き写す

**土台**

- トークン・`reset.css`・`main.css`・Stylelint を、design-system-prac から持ち込む
- Storybook を入れる。Void の plugin が邪魔をしないか確かめる。構成は One UI を参考にし、addon-a11y と addon-vitest を入れる
- dependency-cruiser のルールを足す（`pages/` → `features/` → `ui/`、`features/` 同士は import しない）
- VS Code のタブにフォルダの名前を出す設定（`workbench.editor.customLabels.patterns`）を足す

**実装のハーネス（ZSCM-29）**

- Modern Web Guidance を `googlechrome` のマーケットプレイスから入れる。1 日待ちの例外を、`pnpm-workspace.yaml` の `minimumReleaseAge` のコメントにも書く
- Baseline の目標（Newly available）を `CLAUDE.md` に書く
- `@storybook/addon-mcp` を入れる
- design-system-prac の `.claude/rules/`（部品の置き方・UX のルールなど）を、`apps/web/src/client` に合わせて移す。ファイル名（どこでも `index.tsx`）と、「パーツが複数の部品は `import * as` で読む」は、design-system-prac から変えたところなので書き直す
- `DESIGN.md` の参照のさせ方（ルールの `paths` か、スキルの手順か）を決める
- スキルは「振る舞いとナレッジを分ける」記事の方針で作る（手順は `SKILL.md`、観点は `references/`、道具の名前は書かない）
