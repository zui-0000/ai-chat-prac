# API を決める

記録日: 2026-11-15 / 状態: 決定 / 対象: oRPC 1.16.2、Void 1.6.2

最初の版（`docs/08-機能を決める.md`）に要る API を、手続きの名前のレベルで決めた。
入力・出力・エラーの形は、ストーリーごとの契約のサブタスクで決める。

## 手続きの一覧

oRPC の約束（`packages/contract`）に書く手続きは 5 つ。

| 手続き              | HTTP     | 何をするか                                               | REST で言えば              | ストーリー       |
| ------------------- | -------- | -------------------------------------------------------- | -------------------------- | ---------------- |
| `chat.list`         | `GET`    | 自分の会話の一覧（新しく更新した順）                     | `GET /chats`               | ZSCM-43          |
| `chat.get`          | `GET`    | 会話を 1 つ開く。会話と、そのメッセージを一緒に返す      | `GET /chats/:id`           | ZSCM-43          |
| `chat.create`       | `POST`   | 最初のメッセージを付けて会話を作り、返答を流しながら返す | `POST /chats`              | ZSCM-44・ZSCM-45 |
| `chat.delete`       | `DELETE` | 会話を消す。メッセージも一緒に消す                       | `DELETE /chats/:id`        | ZSCM-43          |
| `chat.message.send` | `POST`   | 会話にメッセージを送り、返答を流しながら返す             | `POST /chats/:id/messages` | ZSCM-44・ZSCM-45 |

約束に書かないもの:

| パス          | 誰が出すか          | 何をするか                                                       |
| ------------- | ------------------- | ---------------------------------------------------------------- |
| `/api/auth/*` | Void（Better Auth） | 新規登録・ログイン・ログアウト・セッション・Google と X の戻り先 |
| `/rpc/*`      | 自分（今もある）    | oRPC の手続きを受ける                                            |

今の約束（`message.list`・`message.create`・`chat.stream`）は雛形なので、メッセージの契約（ZSCM-58）で作り直す。

後で作るもの: 会話の名前を変える（`chat.rename`）、設定（表示名・モデル）

## 手続きは関数、HTTP のメソッドは動きに合わせる

oRPC の手続きは、FE から関数のように呼ぶ。`chat` と `chat.message` は名前の入れ物で、`send` がその中の関数。

```ts
const stream = await client.chat.message.send({ chatId, text });
```

HTTP では `/rpc/<入れ物>/<関数>`（`/rpc/chat/message/send` など）になる。oRPC の FE の部品（`RPCLink`）は、何も設定しないとどの手続きも `POST` で送る。
それでは通信を見ても何をしているか分からないので、メソッドを動きに合わせる。

| 動き                   | メソッド | 手続き                             |
| ---------------------- | -------- | ---------------------------------- |
| 読むだけ               | `GET`    | `chat.list`・`chat.get`            |
| 消す                   | `DELETE` | `chat.delete`                      |
| 作る・送る（それ以外） | `POST`   | `chat.create`・`chat.message.send` |

- `GET` は「読むだけで、何も変えない」ことを表す。何度送っても結果が変わらないので、失敗したときに送り直しても安全
- `GET` の入力は URL に入る。会話の ID くらいの小さな入力なので困らない。URL が長くなりすぎると、oRPC は自動で `POST` に切り替える
- `DELETE` も、何度送っても結果が同じ（2 回目は消すものが無いだけ）。oRPC は `GET` 以外の入力を本文で送るので、`DELETE` でも同じ形で届く
- `chat.create`・`chat.message.send` は書き込み、返答を流して返すので、`POST` にする
- 名前を変える（`chat.rename`）を作るときは `PATCH` にする

oRPC 1.16.2 の仕組みで、次を組み合わせる（設定は ZSCM-66 でやる）。

| どこで             | 何を                                                     | なぜ                                                                                                                                                                                                                  |
| ------------------ | -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 約束（contract）   | 手続きに `.route({ method: 'GET' })` などを付ける        | どの手続きがどのメソッドかを、約束の 1 か所で決める                                                                                                                                                                   |
| FE（`RPCLink`）    | `method` に `inferRPCMethodFromContractRouter(contract)` | 約束に書いたメソッドで送る。FE で手続きの名前を並べずに済む                                                                                                                                                           |
| BE（`RPCHandler`） | `StrictGetMethodPlugin` を切らない                       | 最初から入っている（`strictGetMethodPluginEnabled` が既定で `true`）。`GET` を許すのを約束で印を付けたものだけにし、`chat.delete` などを `GET` で呼ばせない（CSRF を防ぐ）。切ると、どの手続きも `GET` で呼べてしまう |

- 個人の会話を返すので、ブラウザや CDN にためさせない。`GET` の応答には、ためない指示（`Cache-Control: private, no-store`）を付ける
- oRPC の受け口（`src/server/routes/rpc/[...path].ts`）は、今は `GET` と `POST` しか受けない。`DELETE` も受けるようにする
- `POST` と `DELETE` の CSRF も防ぐ。ログインは Better Auth のクッキーで持つので、ほかのサイトから自分のブラウザを使って `chat.delete` などを送らせる罠が作れる。本体はクッキーの `SameSite=Lax`（ZSCM-47 で確かめる）。oRPC の `SimpleCsrfProtectionHandlerPlugin` も使うかは ZSCM-66 で決める（v2 では無くなる。下の「oRPC v2 について」）

## 親子のテーブルは、API も入れ子にする

`t_chat` と `t_message` は 1 対多。1 つの会話にメッセージがたくさんあり、メッセージは必ずどれかの会話に属する。
そのため、メッセージの手続きは会話の中に入れ子にする（`chat.message.send`）。REST の `/chats/:id/messages` と同じ形。

まだ会話が無いとき（`/` で最初に送るとき）は、会話を作る手続き（`chat.create`）を分けた。

| 案                                 | 決めたか   | 理由                                                                                                                              |
| ---------------------------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **会話を作る手続きを分ける**       | これにした | 会話を作るのは `chat`、メッセージを足すのは `chat.message` で、リレーションどおり。入力に「あってもなくてもいい」会話の ID が無い |
| `chat.message.send` 1 つにまとめる |            | 会話の ID が「あってもなくてもいい」入力になり、「まだ無い会話のメッセージ」を足すことになる                                      |

- `chat.create` は、`/` で最初に送ったときにだけ呼ぶ。「会話は最初のメッセージを送ったときに作る」（`docs/08-機能を決める.md`）を守れる
- 返答を流す BE の中身は 1 つの関数にまとめ、2 つの手続きから呼ぶ
- `chat.create` は、流すものの最初に作った会話の ID を出す。FE はそれを見て `/chats/:id` に移り、一覧にも出す
- `chat.message.send` は、会話の更新した日時を進める。一覧を新しく更新した順に並べるため

## 手続きを増やさずに済ませたもの

| 機能                   | 決めたこと                                                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 会話を開く             | `chat.get` 1 つで、メッセージも一緒に返す。`/chats/:id` を開くと両方要る                                                             |
| 返答を止める           | 手続きを作らない。FE が `chat.create`・`chat.message.send` の通信を切り（`AbortController`）、BE はそこまでを保存する                |
| 送り直す               | 手続きを作らない。同じ手続きをもう一度呼ぶ（新しい会話なら `chat.create`）。そのため、失敗した送信は何も保存しない（会話も作らない） |
| Generative UI の選択肢 | `chat.message.send` に「どの選択肢を押したか」を付け、押したことの保存と送信を 1 回で済ませる                                        |
| ログイン中の人を知る   | 手続きを作らない。Void の認証のクライアントが、セッション（名前・メールアドレス）を返す                                              |

- 失敗した送信を保存すると、送り直したときに同じメッセージが 2 つ残る
- 選択肢の保存と送信を別の手続きにすると、片方だけ成功することがある
- メッセージが多くなって `chat.get` が重くなったら、メッセージを別の手続き（`chat.message.list`）に分ける

## テーブルと名前の決まり

| 何       | 決まり                                               | 例                                        |
| -------- | ---------------------------------------------------- | ----------------------------------------- |
| テーブル | トランザクションは `t_`、マスタは `m_`。単数形       | `t_chat`・`t_message`                     |
| API      | テーブルから `t_`・`m_` を外した名前 ＋ 動き         | `chat.list`・`chat.delete`                |
| API      | 親子の関係があるテーブルは、子を親の中に入れ子にする | `chat.message.send`                       |
| URL      | 複数形                                               | `/chats/:id`（`docs/05-画面を決める.md`） |

API とテーブルの名前をそろえ、`chat.delete` を見れば `t_chat` を消すと分かるようにする。
`chat` は「1 つの会話」の意味だけに使う。チャットの画面は、置き場所（`pages/Chat` など）で区別する。docs と画面の文字では「会話」と書く。

最初の版のテーブル:

| テーブル                                             | 中身                                                               | 作るのは            |
| ---------------------------------------------------- | ------------------------------------------------------------------ | ------------------- |
| `t_chat`                                             | 会話。持ち主・名前・作った日時・更新した日時                       | 自分（ZSCM-55）     |
| `t_message`                                          | メッセージ。どの会話か・誰の発言か（人か AI か）・中身・作った日時 | 自分（ZSCM-55）     |
| `t_user`・`t_session`・`t_account`・`t_verification` | 認証                                                               | Void（Better Auth） |

- 会話のテーブルを作るのは、持ち主・名前・更新した日時を持たせるため。メッセージだけだと、一覧のたびに会話ごとの最初と最後のメッセージを探す重い検索になり、消す単位も無くなる
- 認証のテーブルも `t_` にそろえる。Better Auth にはテーブルの名前を変える設定（`modelName`）がある。Void の上で効くかは、認証の BE（ZSCM-47）で確かめる
- Generative UI の部品と押した選択肢は、`t_message` の中身に持たせる。別のテーブルにするかは、ZSCM-62・ZSCM-63 で決める
- 列の型や索引は、BE のサブタスクで決める

## どの手続きにも共通の決まり

次は、3 つのストーリーの契約が全部使うので、別のタスク（ZSCM-66）で先に決める。

- エラーの形（コードとメッセージ。未ログイン・見つからない・AI の失敗など）
- ID と日時の形
- メソッドどおりに送る仕組みと、CSRF の対策（上の「手続きは関数、HTTP のメソッドは動きに合わせる」）

ログインが要る手続きの土台は、Void の認証と一緒に作るほうが自然なので、認証の BE（ZSCM-47）で作る。

## oRPC v2 について

2026-11 時点で、oRPC v2 はベータ（2.0.0-beta.50）。9 月から 2〜5 日おきに出ていて、正式版の日はまだ決まっていない。
最初の版は v1（1.16.2）で作り、v2 の正式版が出たら移行する（ZSCM-67）。ベータは上げるたびに中身が変わり、固定の版で入れる決まりと合わないため。

公式の移行ガイド（Migrating from oRPC v1）で、ここで決めたことに響く変更:

| 何                   | v1（今）                                     | v2                                                                                                                |
| -------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| メソッドの指定       | `.route({ method: 'GET' })`                  | `.route` が無くなり、`.meta(openapi({ method: 'GET' }))` で書く（`.route` を戻す拡張もある）                      |
| GET の受け付け       | `StrictGetMethodPlugin` が最初から入っている | プラグインが無くなる。GET は最初から弾かれ、`allowMethods` で許す。CSRF は `GetMethodCsrfProtectionHandlerPlugin` |
| POST・DELETE の CSRF | `SimpleCsrfProtection…` の組                 | 無くなる。ログインのクッキーを `SameSite=Lax` にして守る                                                          |
| エラー               | `status` を持てる                            | `status` が無くなる。HTTP の状態コードは `errorStatusMap` で決める                                                |
| `RPCLink`            | `url` に全部書く                             | `origin` と `url` に分かれる                                                                                      |
| 通信の形             |                                              | v1 の FE と v2 の BE は話せない。FE と BE を同時に上げる                                                          |

メソッドを動きに合わせる設計（GET・DELETE・POST）は、v2 でもそのまま使える。変わるのは書き方だけ。
v2 のガイドは「GET は HTTP のキャッシュのように本当に要るときだけ許す」と勧めている。oRPC は全部 POST に寄せる考え方だが、GET を許す正式な仕組みもあるので、読む・消す・送るを見分けやすいほうを取った。

移行を楽にするため、v1 のうちから次を守る。

- エラーに `status` を持たせない。HTTP の状態コードは手続きの外で決める（ZSCM-66）
- POST・DELETE の CSRF は、ログインのクッキーの `SameSite=Lax` を本体にする。Better Auth のクッキーの設定を確かめる（ZSCM-47）。v2 でも同じ守り方になる
