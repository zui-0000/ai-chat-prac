# ADR (Architecture Decision Records)

このプロジェクトの意思決定を記録する場所。

**「なぜこうなっているのか」を後から再構築できるようにする**のが目的であり、
コードを見ても分からない、ほかの案と比べて選んだ大きな決定を対象とする。
決定そのものより、**却下した選択肢とその理由**に価値がある。

細かい書き方やコマンドのような、守ることそのものは ADR に書かない。決定から直接出てくる形（置き場所など）は、決定の中身として書いてよい。

## フォーマット

**MADR 4.0.0** に準拠する。

```txt
---
status: {proposed | rejected | accepted | deprecated | superseded by ...}
date: {YYYY-MM-DD}
scope: {all | client | server | contract}
decision-makers: {決定した人}
consulted: {意見を求めた相手（双方向のやりとりがあった人）}
informed: {結果を共有する相手（一方向）}
---

# {解決した問題と採用した解決策を表す短いタイトル}

## 背景と課題 (Context and Problem Statement)
## 決定要因 (Decision Drivers)
## 検討した選択肢 (Considered Options)
## 決定 (Decision Outcome)
### 結果 (Consequences)
### 確認方法 (Confirmation)
## 各選択肢の評価 (Pros and Cons of the Options)
## 補足情報 (More Information)
```

各セクションの書き方は既存の ADR を参照。特に以下の 2 つは形式が決まっている。

**結果 (Consequences)** — 良い点と悪い点を箇条書きで並べる。

```markdown
- Good, because {良い結果}
- Bad, because {悪い結果・トレードオフ}
```

**各選択肢の評価 (Pros and Cons of the Options)** — 選択肢ごとに見出しを作り、
`Good` / `Neutral` / `Bad` で評価する。**採用しなかった案こそ丁寧に書く。**

## 運用ルール

### 対象 (scope)

**どこに効く決定かをフロントマターに書く。** 索引の「対象」列がこれを写す。

| 値         | 意味                                                        |
| ---------- | ----------------------------------------------------------- |
| `all`      | リポジトリ全体。土台・ツール・FE と BE の両方に効く決定など |
| `client`   | `apps/web/src/client` だけ                                  |
| `server`   | `apps/web/src/server` だけ                                  |
| `contract` | `packages/contract` が主題。両端に効くが決定は契約側にある  |

**層でフォルダを分けない。** 分類はトピック（ライブラリ / 設計など）の 1 軸に保ち、
層は `scope` で表す。

### ディレクトリ構成

```txt
docs/adr/
├── README.md          ← このファイル（索引）
├── ライブラリ関連/
│   └── ADR-01-....md
├── 設計関連/
│   └── ADR-01-....md
├── {カテゴリ名}/
└── 未分類/            ← 分類に迷ったらここ（無ければ作る）
```

- **サブフォルダは 1 階層のみ。ネストしない**
- **番号はカテゴリ内でローカルに連番**（グローバル一意ではない）
- 分類に迷ったら `未分類/` に置く。後から適切なカテゴリへ移動する

### ファイル名

```txt
ADR-{NN}-{タイトル}.md
```

- タイトルは**本文の `#` 見出しと揃える**。ファイル名では空白を詰める
- 「〜する理由」のような語尾は付けない。理由を書くのが ADR なので冗長

### 相互参照

- **同一カテゴリ内**: `ADR-02` と書く
- **カテゴリを跨ぐ**: `ライブラリ関連/ADR-02` のようにカテゴリ名を含める

### ステータスの更新

決定が覆ったら、古い ADR を**消さずに** `status` を書き換え、索引の「ステータス」列も直す。

| 値                                    | 意味                    |
| ------------------------------------- | ----------------------- |
| `proposed`                            | 提案中                  |
| `accepted`                            | 採用中                  |
| `rejected`                            | 却下した                |
| `deprecated`                          | 使わなくなった          |
| `superseded by ライブラリ関連/ADR-05` | 別の ADR に置き換わった |

新しい ADR 側には、何を覆したのかを書く。

### 書く粒度

- 迷った末に決めたこと、**却下した案があること**は書く
- 自明なこと、後から誰でも同じ結論に至ることは書かなくてよい
- 1 つの決定に 1 本。いくつもの決定を 1 本にまとめない
- 計測の数字は、決め手になったときに書く（ライブラリを比べたときのバンドルサイズなど）。
  全部の ADR で測る必要はない
- 公開のリポジトリなので、守りの弱いところ（まだ確かめていない守りなど）は書かない
- **完璧なフォーマットを整えるより、1 つ書く方が価値がある**。
  埋められないセクションは消してよい

### コードブロック

**言語を必ず指定する。** 迷ったら `txt`。
