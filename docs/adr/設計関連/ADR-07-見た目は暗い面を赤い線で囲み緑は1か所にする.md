# 見た目は暗い面を赤い線で囲み緑は 1 か所にする

## 背景と課題 (Context and Problem Statement)

部品を作る前に、アプリの見た目の方向性を決める。決めずに部品を作り始めると、色や形を部品ごとにその場で選ぶことになり、画面がそろわない。

リポジトリの管理者が、自分で毎日使うアプリである。ふだん使っているエディタは、暗い面に赤い線の配色にしている。

## 決定要因 (Decision Drivers)

- 毎日使う道具として、長く見ていても疲れないこと
- ひと目でこのアプリだとわかる持ち味があること
- 明るい配色でも成り立つこと
- 文字と線のコントラストを守れること

## 検討した選択肢 (Considered Options)

- 面を赤い線で囲む
- 赤は差し色だけにする
- 赤とオレンジの 2 本線と、等幅のラベルにする
- 明るい紙の色と墨色にする

## 決定 (Decision Outcome)

**選択: 面を赤い線で囲む**

決め手は、**赤を「塗り」でなく「線」で使えば、持ち味を出しながら、面は静かなままにできる**こと。面は無彩色のままなので、長い文やコードを読むじゃまにならない。

- 赤く塗るのは、主な操作のボタンだけにする
- 緑は、返答が流れている途中の印の 1 か所だけに使う
- 光らせるのは、入力欄だけにする
- 発言は、自分の発言も AI の返答も同じ作りのカードにし、ふちの線の左右だけを反対にする
- 暗い配色と明るい配色を持ち、OS の設定に合わせて切り替える。作るときは暗い配色を先に考え、明るい配色では土台と面を明るい色に替えるだけにする。線・印の使い方は変えない
- コードの箱は、明るい配色でも暗いままにする

値はトークン（`apps/web/src/client/styles/tokens/`）に置き、使い分けは `apps/web/DESIGN.md` に書く。

### 結果 (Consequences)

- Good, because 面が無彩色なので、赤い線を引いても文が読みやすい
- Good, because 色の役割が決まっている（赤は線と主なボタン、緑は 1 か所）ので、部品を足しても迷わない
- Good, because 土台と面の色を替えるだけで、明るい配色にもなる
- Bad, because 赤が主役なので、赤だけではエラーや危ない操作だと伝わらない。アイコンと言葉で伝える
- Bad, because 赤は暗い面の上で文字として読めない。文字に使う赤を、線の赤とは別に持つ
- Bad, because 赤い線で囲む面が増えると、うるさくなる。囲む面を増やさない

### 確認方法 (Confirmation)

`apps/web/src/client/styles/tokens/color.css` の「このサイトの色」と役割の色。`apps/web/DESIGN.md` の使い分け。

## 各選択肢の評価 (Pros and Cons of the Options)

### 面を赤い線で囲む — 採用

- Good, because 赤の面積が小さく、長く見ていても疲れにくい
- Good, because 線だけで、ひと目でわかる持ち味になる
- Bad, because 線の赤（面に対して 3:1 以上）と、文字の赤（4.5:1 以上）を分けて持つ必要がある

### 赤は差し色だけにする

枠は灰色にし、赤は入力欄のフォーカスの輪と、送る・止めるボタンだけに使う案。

- Good, because いちばん静かで、長く見ても疲れない
- Bad, because よくある暗い配色のチャットと見分けがつかず、持ち味が出ない

### 赤とオレンジの 2 本線と、等幅のラベルにする

角を丸めず、発言を吹き出しにせずに記録のように並べ、名前と時刻を等幅の小さな字で出す案。

- Good, because 持ち味がいちばん強い
- Bad, because 飾りが多く、毎日使う道具としてはうるさい
- Bad, because 小さな等幅の字が増え、和文の本文と並べると読みにくい

### 明るい紙の色と墨色にする

あたたかい白に墨色の文字を置き、送るボタンだけを朱色にする案。画面に描く前に外した。

- Good, because 文を読むことに向いている
- Bad, because 暗い面に赤い線という、リポジトリの管理者がふだん使う配色から離れる

## 補足情報 (More Information)

案は、色の値を並べて比べず、会話の一覧・発言・入力欄のある画面の形に描いて、並べて選んだ。色の値だけでは、良いかどうかを判断できないため。
