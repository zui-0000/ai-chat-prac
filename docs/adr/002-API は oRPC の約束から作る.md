# 002 API は oRPC の約束から作る

- 状態: 採用
- 日付: 2026-11-08

## 背景

Void の型安全はコード駆動で、型は DB のスキーマ → ハンドラーが返す値 → Void が作るルートの型 → `void/client` の `fetch` の順に流れる。入力と出力の形を先に書く場所が無いので、BE のルートを書くまで、FE と偽物の BE を作れない。

AI チャットでは、さらに次のことが効いた。

- Void のストリーミングのクライアント（`void/sse/client`）は `EventSource` を包んだもので、リクエストの body を送れない。メッセージを送って返答を流して受け取る、が組めない
- 偽物の BE（ADR 003）が満たすべき約束が無いと、偽物と本物の形がずれても気づけない

## 決めたこと

- FE と BE の間の API は、`packages/contract` に oRPC の約束（zod のスキーマ）として先に書く
- BE は Void のルートを 1 つ（`/rpc` の受け口）だけ置き、`/rpc` の下は全部 oRPC に渡す。手続きは約束を `implement` して作る
- FE は約束の型だけを読み、関数のように呼ぶ。偽物の BE も同じ約束を `implement` する
- HTTP のメソッドは、動き（読む・消す・作る）に合わせる
- 手続きを増やさない。止める・送り直す・ログイン中の人を知る、は手続きを作らずに済ませる
- oRPC は v1 で作り、v2 の正式版が出たら移る。v1 のうちから、v2 で無くなる書き方（エラーの `status` など）を使わない

## ほかの案

| 案                                          | 選ばなかった理由                                                                               |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Void の `void/client` の `fetch`            | body を送るストリーミングが組めない。偽物が満たす約束が無い。TanStack Query のキーを自分で持つ |
| 全部の手続きを `POST` にする（oRPC の既定） | 通信を見ても、読むのか書くのか分からない                                                       |
| oRPC v2 のベータを今使う                    | 上げるたびに中身が変わり、固定の版で入れるやり方と合わない                                     |

## 手放すもの

- Void の公式の道から少し外れる。`/rpc` の下は、Void の型付き `fetch` とルートごとのキャッシュの対象から外れる
- v2 に移るときに書き方が変わり、FE と BE を同時に上げることになる
