# FE の書き方

記録日: 2026-11-18 / 対象: React 19.3.1、TanStack Query 5.107.1、@orpc/tanstack-query 1.16.2、Oxlint 1.91.0

`apps/web/src/client/` のコードの書き方を決めた。フォルダの置き場所は `docs/12-FE のフォルダ構成.md`、部品の中の形は `docs/06-デザインシステムを決める.md` にある。

## 名前

| もの                 | 書き方                     | 例                                              |
| -------------------- | -------------------------- | ----------------------------------------------- |
| 部品・部品のフォルダ | PascalCase                 | `MessageList/index.tsx` の `MessageList`        |
| 関数・変数           | lowerCamelCase             | `formatCount`                                   |
| hook                 | `use` で始める             | `useChat`                                       |
| 定数                 | UPPER_SNAKE_CASE           | `MESSAGE_MAX_LENGTH`・`CONTEXT_KEYS`            |
| ファイル             | 中で export するものの名前 | `useCreateMessageMutation.ts`・`formatCount.ts` |

- ファイル名を export の名前にそろえると、import の行とファイルの名前が一致し、検索でも見つけやすい
- 部品はフォルダ名が部品の名前で、ファイルは `index.tsx`（`docs/06` の「ファイル名は、どこでも `index.tsx`」）
- 偽物の BE（`mocks/`）は、約束の階層と同じフォルダに `handler.ts`・`scenarios.ts` を置く決まりなので、今の名前のまま（`docs/04-MSW.md`）

## バレル export を使わない

`index.ts` で `export * from "./hooks"` のようにまとめ直さない。使う側は、要るファイルを直に import する。

- まとめ直したファイルを 1 つ読むと、中の全部を読み込む。開発サーバーは読み込むファイルが増えるほど遅くなり、ビルドでも使わないものを外しにくくなる
- import を見ても、どのファイルに実体があるかがわからなくなる

Oxlint の `oxc/no-barrel-file`（`threshold: 0`）で、`export *` を止める。`export { a } from "./a"` のような名前を付けたまとめ直しは、lint では止まらないので、レビューで見る。部品の `index.tsx` は、部品そのものを書くファイルなので、バレルではない。

## `useMemo`・`useCallback`・`memo` を使わない

`apps/web` は React Compiler（`react({ compiler: true })`）を使っている。Compiler が、値と関数と部品のメモ化を自動で入れる。手で書くと、依存の配列の書き間違いで古い値を使うことがあり、Compiler の判断とも重なる。値を作る計算は `utils/` の関数にして、部品から呼ぶ。

Oxlint の `no-restricted-imports` で、`react` から `useMemo`・`useCallback`・`memo` を import したら止める。`import * as React from "react"` も止まるので、React は名前で import する。

## hooks

- React の公式の hooks は、使えるところで使う
- アプリ全体で持つ状態は zustand のストア（`stores/`）に置く。`createContext`・`useContext` を使うときは、なぜストアではだめかをコメントに書く
- `useEffect` は、ほかの書き方で済むなら使わない
  - 値から作れるものは、描くときに計算する（`utils/` の関数を呼ぶ）
  - 押したときに起きることは、イベントの関数の中で書く
  - サーバーのデータは TanStack Query で取る
  - React の docs の「You Might Not Need an Effect」と同じ考え方。`useEffect` の中で `setState` すると、Oxlint の `react/set-state-in-effect` が止める

## API の取得と更新

`api/` の中は、次の形で書く。

```text
api/
├── orpc.ts                               oRPC のクライアント（client）と TanStack Query の道具（orpc）
├── keys.ts                               コンテキストごとのキー（CONTEXT_KEYS）
└── message/                              コンテキスト（約束の message）
    ├── getMessageListQueryOption.ts      取得
    └── useCreateMessageMutation.ts       更新
```

```ts
// api/keys.ts
const MESSAGE_CONTEXT_KEY = {
  all: orpc.message.key(),
  list: () => orpc.message.list.queryKey(),
  create: () => orpc.message.create.mutationKey(),
} as const;

export const CONTEXT_KEYS = { MESSAGE_CONTEXT_KEY } as const;

// api/message/getMessageListQueryOption.ts
export const getMessageListQueryOption = () => orpc.message.list.queryOptions();

// api/message/useCreateMessageMutation.ts
const baseOptions = orpc.message.create.mutationOptions();

export const useCreateMessageMutation = (
  options?: Pick<typeof baseOptions, "onSuccess" | "onError" | "onSettled">,
) => useMutation({ ...baseOptions, ...options });
```

- キーは `keys.ts` に、コンテキストごとの `<コンテキスト>_CONTEXT_KEY` としてまとめる。`all` を置くと、そのコンテキストの下をまとめて無効化できる
- oRPC の手続きのキーは、`orpc` の `key()`・`queryKey()`・`mutationKey()` で作る。配列を自分で組み立てない。oRPC が作るキーには型が付いていて、`getQueryData`・`setQueryData` の戻り値に型が付く。自分で組み立てると `unknown` になる
- 取得は、`queryOptions` を返す関数（`get〜QueryOption`）にする。部品では `useQuery(getMessageListQueryOption())` と書き、ルートの `loader` でも同じものを使える
- 更新は、`use〜Mutation` の hook にする。呼ぶ側が渡せるのは `onSuccess`・`onError`・`onSettled` だけにし、送り方やリトライは `api/` が決める
- 部品からは `orpc` を直に使わず、この 2 つを使う

`api/` のコンテキストのフォルダと `keys.ts` は、要るようになったときに作る。今の `Chat` の画面（oRPC の疎通確認用の仮の画面）は `orpc` を直に使っている。メッセージの約束を作るときに、この形に置き換える。
